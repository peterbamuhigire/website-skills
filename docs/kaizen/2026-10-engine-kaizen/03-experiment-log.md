## Practitioner tasks

### Service website

The disposable site has five pages and synthetic content. HTML performance lint passes on all five. Route-weight checks pass each route at 50.1 KB total, including 48.6 KB of local fonts; no JavaScript or third-party script bytes are reported by that gate. The fixed axe gate scans all five pages successfully. No real contact destination or service identity was supplied, so this remains a prototype.

Lighthouse CI ran three times per route (15 runs total) under the fixture's configured low-end mobile stress profile. All five route assertions fail the configured 2,000 ms maximum LCP. Across these retained results the reported values span 2,109.2901–2,418.24945 ms; FCP also fails its 1,500 ms assertion. The networking/render-blocking audit warnings are recorded but no threshold was changed. This is local lab evidence; field Core Web Vitals are NOT_ASSESSED.

### Static catalogue

The fixture presents synthetic catalogue content with disabled enquiry/payment controls and explicit missing inputs. New skill instructions require seller-approved destination and response owner before enabling enquiry, and verified provider, merchant, price, currency, stock, fulfilment, refund, reconciliation and access-control inputs before proposing manual settlement. This is guidance and a static artifact, not a live payment flow or validated commercial operation.

### Deliberately defective page

The accessibility gate detects one critical and two serious findings on the bad fixture and exits nonzero. Slop scan blocks three findings. HTML lint reports two errors: image dimensions absent and `document.write`. Metadata audit reports a four-character description plus missing canonical, social title, and image metadata. These are expected fixture failures, not defects in a real client website.

## Dependency remediation and controlled performance experiments

The exact temporary consumer lockfile had 15 high package vulnerability records. Plain `npm audit fix` made no remediation; its audit report still gave only forced top-level changes to `@lhci/cli@0.1.0` and `serve@10.0.2`. A disposable copy used a scoped npm override `{"overrides":{"serve":{"compression":"1.8.2"}}}`. The changed lockfile removed only the nested `serve/node_modules/compression@1.8.1` entry and deduplicated it to the already present `compression@1.8.2`. Audit results became 13 high, zero critical, one moderate, and two low. This fixes the one compression advisory record only; the canonical security gate remains blocked.

On the override copy, the clean accessibility and SRI checks still pass, deliberate negative fixtures still fail, the clean slop check passes, and the full five-route Lighthouse run has the same LCP failure profile. This supports the override as a scoped patch for the compression dependency, not as a full security remediation. No consumer lockfile or engine runtime package file was changed in the checkout.

For LCP, all variants used the same local LHCI static file server, Chrome binary, Lighthouse settings, and `compression@1.8.2` override. A clean minimal page with no CSS or fonts passed the LCP assertion: three runs ranged 1,502.8–1,518.8 ms. A copy of the service page with its CSS retained but custom font-face declarations/usages removed passed LCP in three runs at 1,806.2–1,813.5 ms. The same copy with the font files preloaded but system fonts used failed at 2,111.9–2,121.9 ms. The full custom-font site failed across five routes and 15 runs at 2,405.2–2,422.7 ms; its largest-contentful element is the H1, and Lighthouse attributes 903.3 ms to TTFB and 1,506.6 ms to render delay on the inspected contact route. The same report records 4 ms observed server response, zero redirects, and 0.8 KB HTML / 0.7 KB CSS / 48.6 KB fonts on the route.

These controlled variants indicate that the failure comes from this fixture's local font/CSS rendering under the 4x CPU and simulated mobile network profile, rather than measurable static-server response delay (inference). Preloading fonts while using fallback faces still missed LCP, while omitting the font resources and font use passed. The test isolates both font transfer and font/render work as contributors; it does not prove which change should ship on a real project. No LCP budget or gate was relaxed.
