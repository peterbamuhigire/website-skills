# Kaizen conversion experiment loop

[Owning skill](../SKILL.md)

Use this reference to turn a website conversion question into a small, reversible learning cycle. It combines Lean's validated-learning orientation with the participatory, incremental, low-budget, standardising emphasis described in *Applying the Kaizen in Africa*.

## Source basis and limits

- *LEAN: Ultimate Collection* (2018) supports Build-Measure-Learn, validated learning, innovation accounting, KPI cadence, waste/value analysis, and experimentation. The compilation is uneven and duplicated; use current primary sources for exact statistical or platform rules.
- *Applying the Kaizen in Africa* (2018) supports PDCA, 5S, muda removal, on-site observation, participatory improvement, QC Story, standardisation, management commitment, and low-cost incremental change. Its case evidence informs adaptation; it does not guarantee a result for a particular website.

## Delivery loop

1. **Observe:** inspect the real route, support questions, search terms, analytics events, failed submissions, and representative user evidence. Record the observation date and source.
2. **Baseline:** define the user task, denominator, primary outcome, time window, segment, current value, and guardrails. Clean event names and remove duplicate or unused instrumentation as an analytics 5S pass.
3. **Select:** choose one high-leverage defect or uncertainty. Prefer a reversible content, hierarchy, copy, form, or CTA change over a broad redesign.
4. **Experiment:** write `Changing [one element] from [A] to [B] will improve [metric] because [audience reason]`, with a minimum meaningful effect, owner, timebox, stop rule, and rollback.
5. **Check:** verify exposure, event integrity, accessibility, performance, privacy, content truth, and qualitative feedback before interpreting conversion movement.
6. **Standardise:** only promote a learning when the primary outcome improves without violating guardrails. Update the owning page pattern, reference, or component and record the version.
7. **Teach:** add the learning to the handoff, design/content system, and team review so it is not trapped in a report.
8. **Re-measure:** set the next baseline and date the next review. A failed or inconclusive test is still evidence if the decision and limitations are preserved.

## Decision table

| Result | Decision | Required evidence |
|---|---|---|
| Primary metric improves and all guardrails pass | Standardise the narrow change | Exposure check, metric analysis, accessibility/performance/security evidence, before/after record |
| Metric improves but trust, accessibility, performance, privacy, or error recovery worsens | Reject or roll back | Guardrail failure and recovery evidence |
| No reliable movement or telemetry is broken | Keep baseline, repair evidence, and iterate narrowly | Data-quality note and next hypothesis |
| User value is unclear or the page addresses the wrong problem | Stop conversion optimisation and return to experience mapping | Audience action map and research gap |
