# Enterprise Internal Tools and Portal UX

Parent skill: [premium-ui-ux-design](../SKILL.md). Read when the website engagement includes a client portal, staff intranet, back-office screen, broker or agent tool, or when you must explain to an enterprise buyer why UX work is more than styling.

Use with `enterprise-five-outcomes.md` (launch gate), `enterprise-website-ux-playbook.md` (public enterprise sites), `../../../quality-gates/design-quality-score/references/enterprise-ux-maturity-checklist.md` (process maturity) and `../../../build/design-system/references/enterprise-data-viz-rules.md` (dashboards).

## 1. Explain UX versus UI to the buyer

- **UI** is the medium: what people see and touch to talk to the system. Good UI improves look and feel; it does not by itself make a product useful or usable.
- **UX** is how the parts work together: the balance of usefulness, usability and aesthetics, and how people feel using it.
- A polished interface on a broken information structure is still a failed product. Budget for research, structure and interaction before styling.
- Plain analogy for non-designers: code is the skeleton, UX is the organs that keep the body working, UI is the appearance and senses. UX comes first; UI is a subset of it.

## 2. Business case talk track (no invented figures)

Frame the case around outcomes the buyer can verify in their own data:

| For customer-facing products | For internal tools |
|---|---|
| Higher satisfaction and brand perception | More satisfied, more productive staff |
| Lower acquisition cost | Less training and faster ramp-up |
| Lower support cost | Smaller support load and less documentation |
| Higher retention | Fewer errors and less rework |

Rules:

- Ask the client for their baseline numbers (support tickets, training hours, task time, error rates) and promise to measure against them.
- Do not quote generic return-on-investment multiples from vendor reports unless you have checked the original study and its method; say "check the source before stating it".

## 3. Diagnose the current product

Common enterprise failure symptoms and the question each raises:

| Symptom | Question to ask |
|---|---|
| Feature overload | Which user goals does each screen serve? |
| Designed without user research | Who was observed or interviewed, and when? |
| Inconsistent screens | Is there a documented pattern library and who owns it? |
| Look dictated by the technology stack | Were design decisions made by the framework's defaults? |
| Cluttered information | Is there a content strategy and hierarchy per role? |

## 4. Internal applications (back office, operations)

Design internal tools to the same standard as consumer products; only motivation and environment differ.

1. **Design for goals, tasks and context of use.** For every screen, state what the user wants, how they will use it and why. Record the environment (shared desk, warehouse floor, field tablet, poor connectivity, interruptions).
2. **Keep it clean and calm.** Few colours and images, one appropriate typeface family without ad hoc bold and italic mixes, flat surfaces rather than heavy shadows, and generous spacing between content groups.
3. **Structure before screens.** Product owners tend to add features; a clear information structure and flow keeps them usable. Count how often each scenario occurs per user per day and optimise the most frequent ones first.
4. **Make it fast.** Choose a technical approach that keeps interactions responsive; staff notice every delay many times a day.

## 5. Intranets, HR portals and content-managed staff sites

These have a guaranteed audience of every employee, so small improvements multiply.

1. **Findability.** Staff should never waste time working out where things are: clear calls to action, quick links to the most used tasks, and search when content volume demands it.
2. **Role-based content strategy.** Different roles need different content; keep it current. Assign an owner and a review date to every section.
3. **Welcoming look and feel.** Express the organisation's culture through restrained imagery and messaging so staff feel welcomed, not processed.

## 6. Portals and multi-channel service

- Map the channels the customer actually uses (web, phone, WhatsApp, SMS, email, branch, agent) and make the portal consistent with them.
- Detect the intent of each channel. Never place upsell or promotional content in a complaint, claim or support flow.
- Design hand-offs between channels so the customer does not repeat information.

## 8. User interview question set for enterprise tools

Cover five areas in every interview:

1. **Process.** How do you do this task today? How would you like to do it?
2. **Devices.** Which device do you use for most of this work?
3. **Preferences.** What do you like and dislike? Which websites or apps, especially outside this industry, do you find work well?
4. **Exposure.** How many other systems do you use for your job?
5. **Context.** Where and when do you work (office, home, field, shifts)?

## 9. Usability review questions

Check every primary flow against five components:

| Component | Question |
|---|---|
| Learnability | Can a first-time user complete the basic tasks without help? |
| Efficiency | Once learnt, how quickly can the task be done? |
| Memorability | Can an occasional user return after weeks and still succeed? |
| Error handling | When errors happen, does the system prevent, explain and help recover politely? |
| Satisfaction | Does the system carry the user forward, rather than the user driving the system? |

Also check: consistent styling and behaviour for similar tasks, the logo returning to home, confirmation after every submission and loading feedback for every wait, familiar words (sign in, register) rather than invented vocabulary, a route to contact details from every page, and removal of content that adds nothing.

## 10. Iterative design-thinking loop for enterprise projects

Research (users and stakeholders) → define (needs) → ideate → prototype → test with end users → loop back to ideate or prototype until validation passes → deliver a proof of concept or MVP. Record the evidence for each pass so the maturity checklist can be scored.
