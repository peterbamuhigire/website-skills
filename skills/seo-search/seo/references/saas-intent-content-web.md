# SaaS intent coverage and comparison pages

Return to [seo](../SKILL.md). Use for an approved SaaS content architecture or
a social-to-website journey. This is a human-usefulness planning method, not
a separate AI ranking requirement. See the [dated evidence review](../../../../docs/continuous-improvement/2026-09-19-linkedin-aeo-kaizen.md).

## Map real questions; select useful pages

Build an intent matrix across use case, integration and audience. Record an
actual question or evidence of need for each candidate. Do not publish the full
Cartesian product. Merge candidates that solve the same task; reject combinations
without product support, distinctive value or maintainable evidence.

| Page role | Minimum useful content | Natural next destination |
|---|---|---|
| Use case | Reader task, constraints, workflow, suitability and limitations | Relevant template or feature |
| Template | Inspectable example, instructions, prerequisites and real availability | Feature or product |
| Feature | Capability, limits and a reproducible example | Documentation or integration |
| Integration | Supported connection, setup, data flow, prerequisites and failure path | Guide or product |
| Industry | Distinct sector needs and supported fit; avoid cloned sector names | Use case or evidence |
| Comparison / alternative | Named decision criteria, dated facts for both products and trade-offs | The appropriate product, guide or trial |

Treat use case → template → feature → integration → product as one possible
journey. Link only where it helps the reader's next decision; no compulsory
sequence, all-to-all linking or arbitrary link quota.

For each candidate produce:

`intent_id | question evidence | audience | use case | integration | existing URL |
page role | unique value | source IDs | create/merge/reject | canonical URL |
contextual links | CTA | owner | review trigger`

## Make a fair comparison

Confirm product identity, version or plan, market and verification date. Use
vendor documentation or an observed product test for each material cell.
Compare on the same basis; disclose relevant limits and where the competitor
is the better fit. Mark unavailable facts unknown rather than inferring absence.
Avoid unsupported superlatives, false independence and copied competitor copy.

Use a table when it makes the decision easier to inspect, with columns for
criterion, our product, alternative, source/date and limitation. Tables do not
carry an assumed AI citation advantage. Recheck facts when either product changes.
If prices are relevant, route their treatment through the finance doctrine and
verify the applicable plans and currency; do not fill gaps from memory.

## Apply the quote test and technical checks

Ask whether a sentence still states a correct, useful fact when read by itself.
Keep its subject, scope, condition and material limitation together. Prefer clear
explanation over a fixed answer length. Check against the source; an attractive
sentence is not evidence. Do not insert instructions telling assistants to rank
or recommend the product.

Check important content in fetched HTML and rendered output, working navigation,
canonical and index signals, and structured data consistent with visible facts.
Document actual rendering limitations; do not claim that all crawlers are unable
to process JavaScript. Use [Google AI Search](../../google-ai-search/SKILL.md)
for Google-specific eligibility and [crawler guidance](llms-txt-and-ai-crawlers.md)
for optional text artefacts. Keep SEO fundamentals in place.

MCP is a connection protocol for AI applications and external capabilities, not
proof of public discovery or automatic recommendation. Consider it only for a
named client and user task, with a supported connection, authorised data scope,
failure handling and an owner. Hand engineering work to the canonical engineering
engine; a static website content brief does not authorise a new service.

## Social handoff and measurement

Accept the post ID, audience question, promise, approved proof, destination and
CTA from the social engine. Return the canonical URL, publication state, resource
version, fulfilment behaviour, analytics identifier and correction owner. Verify
that the destination fulfils the post without changing its offer or hiding limits.

Measure distinct outcomes: observed answer mentions, supported citations,
referrals and qualified actions. For an AI-answer study retain exact prompts,
brand set, provider/model or unavailable-version note, date, locale, retrieval
mode, repetitions, raw answers, cited URLs and counting rules. Keep branded and
unbranded prompts separate. A mention share uses counted brand mentions as its
denominator; answer presence uses eligible answers. Neither is market share.
No crawl count establishes how often a model repeats a claim.

## Pilot, acceptance and recovery

Select one evidenced intent and improve its existing destination before adding
pages. Keep a comparison page only if it answers a distinct buyer decision.
Check normal navigation and at least one unavailable integration, stale fact,
empty resource or broken-link path. Set a baseline, observation window, owner
and success rule before launch; retain raw evidence and production effort.
Hold publication on unsupported claims or contradictory facts. Restore the prior
copy or remove the broken link, repair the source, and retest. Standardise only
the measured learning; record unmeasured citation or conversion effects as
`NOT_ASSESSED`.
