# Phase 4 - Design System and Build Standardisation

## Objective

Create a premium, repeatable build standard that ensures every project feels custom, looks
expensive, performs well, and can be delivered efficiently without collapsing into templates.

## Why This Phase Matters

The repository already has strong website-building skills, but premium delivery requires a tighter
system of reusable decisions:

- visual tokens
- layout standards
- component patterns
- content modules
- page section libraries
- motion rules
- photo standards

The goal is not to make every site look the same. The goal is to create a disciplined internal
system that makes differentiated sites easier to produce.

## Core Outcomes

- standardize a premium design and build baseline
- create reusable section and component inventories
- tighten skill handoffs between design-system, photo-manager, page-builder, and sector skills
- close weak or stub coverage that undermines premium website execution

## Workstreams

### 1. Define the premium front-end standard

Lock the minimum technical and visual standard:

- Astro-first static or hybrid website architecture
- Tailwind token strategy
- strict typography rules
- image performance rules
- motion rules
- accessibility rules
- responsive behavior rules

### 2. Build reusable section systems

Define a reusable catalog for:

- hero sections
- proof bands
- service grids
- process sections
- testimonial systems
- FAQ systems
- CTA endings
- team and credential modules
- pricing and package sections
- case study layouts

Each section type should include:

- when to use it
- what content it requires
- proof burden
- visual variants
- mobile considerations

### 3. Strengthen design-system outputs

Expand `design-system` so it consistently produces:

- typography hierarchy
- color token map
- spacing scale
- component visual language
- animation guidance
- image treatment rules
- iconography rules

### 4. Resolve repository weaknesses that affect premium delivery

From the analysis, this phase should explicitly address:

- completing or consolidating `webapp-gui-design`
- ensuring `page-builder` contains clear page and component conventions
- strengthening `photo-manager` standards for premium asset selection
- validating `design-reference` to prevent imitation without interpretation

### 5. Build a quality sample library

Create internal sample outputs for the most commercially important sectors:

- professional services
- legal
- healthcare
- education
- authority-focused local business

The point is to give the agency a repeatable benchmark for quality and proof of capability.

## Repository Outputs Required

- section library documentation
- premium component and layout conventions
- improved design token standards
- completion or deprecation plan for weak design-related stubs
- sample benchmark pages or reference builds

## Success Criteria

- new sites can be built faster without looking templated
- every project starts from a strong premium baseline
- design decisions are tokenized enough to scale
- component and page patterns are explicit and reusable
- the repository has no obvious weak point in its core website build workflow

## Risks to Avoid

- confusing standardization with sameness
- letting components multiply without governance
- prioritizing novelty over readability and trust
- keeping weak stubs in the middle of the core build path
- building fancy visuals that are expensive to maintain

## Reading Material To Buy And Provide At This Stage

- *Refactoring UI* by Adam Wathan and Steve Schoger: practical premium interface judgment
- *Designing Interfaces* by Jenifer Tidwell, Charles Brewer, and Aynne Valencia: reusable interface patterns
- *Practical UI* by Adham Dannaway: layout, spacing, and clarity for modern interfaces
- *Grid Systems in Graphic Design* by Josef Muller-Brockmann: disciplined layout foundations
